## Follow-up review repairs

1. Native ordinary-message IDs also appear in pinned, saved and search views. Their explicit deletion now invalidates local copies and old-backup recovery; only Telegram's scheduled, quick-reply and welcome-message ID namespaces are excluded.
2. Date-range archive cleanup no longer runs before the server request. A method-scoped wrapper observes only the owning range's deleteHistory request and final successful affectedHistory response. Errors, partial completion and late callbacks after logout cannot commit a range tombstone. Native callbacks, timestamps, exceptions and requests remain intact.
3. Document staging uses AES-GCM with a random process-only key, never a plaintext temporary JSON file. Operations are account-bound; logout/account changes cancel provider I/O and unlink staging before potentially blocking provider closes. Startup removes previous-process ciphertext and legacy plaintext files in the module-owned namespace. User-selected backup files remain plaintext by design, with the existing warning.
4. Opening the database can recover prior-process logout markers but cannot release this process's active revocation. Marker removal and revocation share the same session lock. Old and revoked-period tokens stay invalid.
5. Ordinary forum entry uses the actual native `Integer.MAX_VALUE` highlight sentinel; explicit message/date navigation still wins. The real-APK gate verifies the constructor assignment, not merely field existence.

The sentinel gate exposed a conservative DEX scanner bug: a one-register object result discarded its neighbouring integer constant as though it wrote a wide pair. Register invalidation now follows actual Dalvik destination widths; minimal-bytecode object/wide/move16 fixtures cover the failure.

## Release workflow

`main` is an ancestor of the historical development branch and can be advanced without discarding its history. The signed candidate is built on the existing trusted development branch, tested before main is advanced, and released from the exact tested source. Workflow guards recognize only the two named trusted repository branches; PRs/forks receive no signing key. The signing environment separately enforces its approved branch policy.

Cloud provenance, installed-package comparison, actual phone results and restoration will be recorded after those steps complete. Static and controlled tests do not certify server privacy, bot-server behaviour, real logout, every forum/device/theme combination or non-Play clients.
